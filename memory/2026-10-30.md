## Инцидент: whole-die decode 100% CPU 15+ мин, ETA 0:00 навечно (die 1878f0e5, 9246×6063)

- Симптом: свип жрёт проц, "0:00 left" всегда, результата нет.
- Причина 1 (снежный ком): Node-fetch (undici) рвёт ответ при idle body
  > 300 с. Декод-POST молчит в ответе 20–30 мин → каждая попытка умирала
  ровно через ~309 с, postWithRetry спавнил НОВОГО воркера, а старые
  продолжали считать. Набилось 6 воркеров × ~1.5 ГБ, 100% CPU на всех,
  каждый захватывал (и тормозил) те же full.json/progress.json.
- Причина 2: job_id уходил внутри body-JSON, а sidecar читает его
  отдельным Form-полем → Stop/cancel не адресовал воркеров.
- Причина 3 (фейк-прогресс «0:00 left»): ProgressWriter калибрует веса
  ТОЛЬКО по записанным стадиям прошлого прогона → незаписанным стадиям
  (graph/runs/outlines/write) вес 0 → сразу после skeletonize pct=100%,
  eta=0, хотя graph реально шёл ещё ~10 мин.
- Причина 4: сама graph-стадия wire_runs._build_graph — питоновский
  пер-пиксельный проход коридоров; на 56 Mpx — минуты (×CPU-contention).
- Оперативно: taskkill /T 5 осиротевших воркеров, последний доработал до
  своего 30-мин дедлайна в sidecar; сидекар перезапущен.
- Фиксы: backend vectorSweep — undici Agent(bodyTimeout/headersTimeout=0)
  в postSidecar (+ dep undici) — один POST теперь держит весь 30-мин
  decode; job_id дублируется отдельным Form-полем. ml/sidecar.py — jid из
  body как fallback + DECODE_SAVE_TO: повторный старт/ретрай JOIN'ает
  уже идущий воркер (ждёт его full.json), близнецы не спавнятся.
  ml/decode_worker.py — калибровка весов merge'тся с DEFAULT_STAGE_MS
  (незаписанным стадиям остаётся дефолтный вес) → pct/eta честные.
- Хвост на потом: graph-стадию хорошо бы векторизовать (numpy/по-блочно),
  иначе большие чипы всё равно будут крутиться минутами.

  ("invalid onRequestStart method" — разные инстансы undici) → свип упал
  "fetch failed" на 0/15. Итог: длинный decode-POST идёт через undici's
