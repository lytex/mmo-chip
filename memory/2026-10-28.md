## desktop:build:win — починен electron-builder

- `npm run desktop:build:win` падал на `pkg:win`: `"electron-builder" не является командой`.
- Причина: в `desktop/` никогда не ставились devDependencies (`desktop/node_modules` отсутствовал).
- Первая попытка `npm install` в desktop упала: electron postinstall не мог скачать бинарник с github — DNS резолвит github.com / objects.githubusercontent.com / npmmirror.com в 127.90.2.x (loopback, DNS-блокировка). Hosts чистый.
- Выяснено: в git global proxy настроен `http://127.0.0.1:10809` (v2ray), прокси живой. npm registry ходит напрямую.
- Решение:
  1. `ELECTRON_GET_USE_PROXY=1` + `GLOBAL_AGENT_HTTPS_PROXY=http://127.0.0.1:10809` (+ HTTP(S)_PROXY) → `npm install` в desktop прошёл (405 пакетов, electron 33.4.11 встал).
  2. electron-builder (app-builder.exe, Go) понимает обычные `HTTPS_PROXY` → с ними `npm run pkg:win` собрался.
- Результат: `desktop/build/dist/mmo-chip-0.1.0-win.zip` + `win-unpacked`. Стейджинг и bins с прошлого прогона не пересобирались.
- Урок: для всего, что качает с github (electron postinstall, app-builder), на этой машине нужно прокси-окружение. `ELECTRON_GET_USE_PROXY` обязателен для @electron/get — обычные HTTP(S)_PROXY он игнорирует.

## Desktop: многопользовательские режимы (--serve / --connect)

- Задача: сервер стартует один человек, остальные — только клиенты (браузер/electron-окно).
- Выяснил: бэкенд УЖЕ многопользовательский (слушает все интерфейсы, раздаёт фронт сам, JWT+LoginPage, presence в WS `user/online`), однопользовательский только Electron-шелл. Решение — флаги в `desktop/main.cjs`, бэкенд не трогали.
- Реализовано в `desktop/main.cjs`:
  - `--serve` (или `MMOCHECK_ROLE=server`): спавн бэкенда, окно НЕ открывается, трей-иконка (встроенный PNG 16×16, зелёная точка — иконок в пакете нет) с меню: LAN URL списком, «Копировать ссылку», «Открыть окно», «Выход». `window-all-closed` в serve-режиме НЕ гасит процесс. Второй запуск `--serve` = «показать окно».
  - `--connect <url>`: без спавна бэкенда, окно грузит удалённый сервер; URL сохраняется в `userData/connection.json` → последующие запуски без флагов переподключаются. `did-fail-load` → диалог «Повторить / Закрыть».
  - `--local`: забыть remote-подключение, вернуться к локальному бэкенду.
  - `desktop:info` теперь отдаёт фактический `backendUrl` (remote в connect-режиме); `.info()` фронтендом пока не вызывается — семантика свободна.
- Решения/нюансы: single-instance lock общий на userData → сервер+клиент на одной машине конфликтуют (клиент становится «показать окно» сервера); для теста/одновременного запуска — `--user-data-dir=`. Auth по договорённости НЕ включаем принудительно (своя LAN). Клиентская сборка та же — staging с бэкендом в remote-режиме просто не используется.
- Смоук-тесты через логи (%APPDATA%\mmo-chip\logs\mmo-chip.log): serve — бэкенд поднялся, LAN URL напечатаны, окна нет; connect с отдельным user-data-dir против живого сервера — бэкенда нет, connection.json записан; обычный запуск — регресса нет. `node --check` ок.
- Изменён только `desktop/main.cjs` (+192/−11).
- Примечание: PS 5.1-смоук с Start-Process + taskkill раз упёрся в таймаут шелла, но процессы электронa не остаются висеть — проверять по логу, а не по выводу команды.

### Правка после полевого теста (лог из E:\boron\logs)

- Симптом: `--connect 10.189.0.16:3101` на другом ПК падал, а «на этом же ПК работает».
- Причина 1: пользователь вводил `-connect` с ОДНИМ дефисом — флаг не распознавался, приложение молча запускало ЛОКАЛЬНЫЙ бэкенд (в логе mode: local). «Работал» локальный режим, не подключение.
- Причина 2: валидация требовала схему — голый `host:port` отвергался («ожидался http(s) URL»).
- Фикс в main.cjs: (1) даш-канонизация argv — `-connect` ≡ `--connect` (значения типа URL не начинаются с `-`, проходят как есть); (2) `normalizeServerUrl` теперь принимает bare `host:port` (схема http:// подразумевается) и подставляет порт 3101, если у http-URL порт не указан; https — без подмены порта. Сообщение об ошибке `--connect` теперь с примером.
- Юнит-проверка normalizeServerUrl (8 кейсов) и parseConnectArg (6 кейсов) — ок; живой смоук: `-connect 10.189.0.16:3101` и `--connect 10.189.0.16:3101` → mode: connect, бэкенд не спавнится, connection.json записан.
- Про «русские символы не отображаются в консоли»: лог-файл пишется в UTF-8 и там всё ок; кракозябры — только в консоли из-за кодовой страницы (chcp 866/1251 вместо 65001). Косметика, не чинил.

### Починены кракозябры в консоли (serve-режим)

- Причина: Electron main-process `console.log` на Windows пишет UTF-8 байты, а консоль (conhost) рендерит их по OEM-кодовой странице cp866 → `тАФ`, `╨║╨╛╨╗╨╗╨╡╨│╨╕`.
- Фикс: `initConsoleCodepage()` в main.cjs — перед initLogging, при `process.platform === "win32" && process.stdout?.isTTY`, `spawnSync("cmd.exe", ["/d","/c","chcp","65001"], { stdio: "ignore", windowsHide: true })`. Кодовая страница — свойство консоли, chcp из чайлда действует и на родительскую консоль. Первые 1–2 строки (до app.whenReady) могут остаться кракозябрами — это баннер, не важно.
- Побочка: после этого ВСЯ консоль рендерится как UTF-8 (включая вывод других инструментов в этой консоли). Для Windows Terminal обычно и так UTF-8 — вызов безвреден.
- Проверить вживую может только юзер (мои шелл-запуски идут через пайпы, isTTY=false → ветка не срабатывает). См криптографию логов: `node --check` + смоук serve — ок, в логе кириллица чистая.
