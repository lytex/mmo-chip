## SPICE handoff round 4 — "Go to SPICE results" restores the whole page

**Task:** after the handoff from the card-dialog agent run, the SPICE Simulation
page must be fully configured — the right models selected, the agent's real
directives in the ngspice directives field, the real testbench — so the user can
just press Run and get the SAME result the agent got, edit the testbench, and
use the Agent on the SPICE tab to refine the tb the agent created.

### The five gaps that were there

1. `directives` was never set on handoff — the field kept whatever was in
   localStorage for that die/subcircuit.
2. `modelSelection` / `customModels` were never set — the models were baked
   into the netlist text only, so the picker disagreed with the netlist.
3. `netlistOverride` was set to the backend's raw run netlist, including the
   `.control` block (`save` / `run` / `write sim.raw` / `quit`) and the trailing
   `.end`. `sanitizeNetlistForRun` keeps `.control` verbatim, so pressing Run in
   the simulator would have executed a second `run` and `quit` out from under
   the worker.
4. With an override active, `setDirectives` was a no-op — the SPICE-tab agent's
   edits never reached Run.
5. `.control`/`.end` leaked into the testbench view netlist.

### The design that fixed them

Do NOT keep the agent's netlist as an override. Decompose the handoff and feed
each piece back into the page's own state:

- `dut` — models + DUT as actually simulated → new `handedDut` state, used for
  `dutNetlist` only while the selected subcircuit still matches the handed DUT
  name (or nothing is selected). Picking a different subcircuit reverts to the
  page's own DUT, no extra wiring needed.
- `directives` — the testbench with `stripRunScaffolding` applied (drops the
  runner's `.control` and the trailing `.end`; keeps `.print`, `.save`,
  `.measure`, sources, analysis). Safe because `save` only limits what is
  *written* to the raw file — the solver computes everything — and round 3
  already filters traces client-side.
- `modelCards` / `modelSelection` / `customModels` — new `optionForCard` +
  `restoreModelSelection` in `shared/src/spiceModels.ts` match the cards back
  against the library, so the picker's radio buttons move to what was simulated
  and unmatched cards stay as the user's own.

`splitAtSectionMarker` in `shared/src/spiceNetlist.ts` does the split on the
section marker (`* ── Testbench ──` from the backend, `* ── Directives ──` from
the composer) and returns `dut: null` when there is no marker — guessing would
duplicate the testbench on recompose.

Auto-run switched from a string compare (`pendingHandoffRun`) to a nonce:
the handoff effect queues `pendingHandoff`, a second effect declared after
`useDirectives` lands it in page state (a render must happen in between, because
the directives hook reloads itself from storage whenever the subcircuit changes
and would otherwise wipe the agent's testbench a moment later), and it bumps the
nonce. By the time the nonce effect runs, `runRef` holds the recomposed netlist.

`useSpiceAgent.buildSimNetlist` now emits `* ── Directives ──` and splits with
the shared `splitAtSectionMarker` instead of its own `extractDutOnly` regex,
which did not recognise `* ── Testbench ──` — with a handoff active that let
the testbench leak into the "DUT" and get appended a second time.

`stripModelCards` also drops a `* ── Models ──` label now, so a netlist that has
been composed once does not come back with two of them.

## SPICE run round 5 — "Error: no data saved for Transient analysis; analysis not run"

**Task:** the card-dialog agent cannot launch the transient simulation; it
blames duplicated `.tran` directives coming from `directives` + `testbench`.

### Root cause (reproduced locally with ngspice-47, `C:\Program Files\Spice64`)

Not the duplicate directives. Duplicated `.tran` runs twice without an error —
it only wastes a run. The killer is the **`save` line the runner emits** in its
own `.control` block (`assembleNetlist`), built from `plan.signals`
(`requestedSignals` → `.print`/`.save`/`.measure` vectors):

- ngspice `save` (and the `.save` dot card) with **no** vector the circuit has →
  `Not saved! Error: no data saved for Transient analysis; analysis not run`,
  the analysis never runs, and `sim.raw` ends up holding only the **constants**
  plot. The tool then reported *"ran no analysis: the netlist has no
  .op/.dc/.tran/.ac directive"* — a misleading message, because the `.tran` was
  right there in the deck. `.print` with a bad name only warns (non-fatal),
  `.measure` with a bad name only fails that measurement (non-fatal) — only
  `save`/`.save` abort. Mixed lists (one valid + one bogus) also survive, so
  the run fails only when *nothing* in the list resolves.
- Real trigger: `.measure`/`.print` naming a node that does not exist at the
  top level (a node inside a `.subckt` written bare, or a net name typo).

### What changed

- `shared/src/spiceNetlist.ts`: new `buildSignalIndex` / `resolveSignals` /
  `sanitizeSignalDirectives`. Nodes/devices of the deck are indexed per
  `.subckt` scope; a bare internal node is rewritten to `v(<instance>.<node>)`
  (unique instance only — ambiguous cases are reported, not guessed), unknown
  vectors are dropped with a note, `.save`/`.print`/`.plot` directives are
  validated the same way (`.save all` and friends are keywords and survive).
- `backend/src/assistant/spiceSimTool.ts`:
  - `planNetlist` sanitizes the directives and resolves the save list before
    splitting the deck; duplicate analyses and duplicate `.measure` lines are
    dropped with a note that says duplicates never change the result;
  - safety net: when ngspice still aborts with "no data saved", the analysis is
    re-run once **without** the save filter (raw file stays big, run succeeds);
  - the constants-plot / no-raw error now says the save list aborted the run
    instead of "there is no analysis directive";
  - tool description + `testbench`/`directives` parameter text carry the
    contract: ONE analysis directive (never in both fields), only nets that
    exist, no `.control`/`.save` guesses.
- Prompts updated: card-discuss system prompt (`llmGraphAnalysis.ts`) and the
  `/assistant/spice-chat` prompt (`api/assistant.ts`) say the same things.

**KEY ARCHITECTURAL DECISION - why a subprocess, not a direct import:**
`backend/tsconfig.json` pins `"rootDir": "src"` + `"include": ["src"]`, so a
backend module importing `../../frontend/src/...` would break
`npm run build -w backend`. The repo's own tests get away with it only because
`*.test.ts` are excluded from the build. Running the extraction as its own
process from the repo root sidesteps this AND isolates the WASM/zustand
globals from the server. Measured cost: 0.49s cold / 0.48s warm - no need for
a persistent worker.

**THE namedNets BUG WAS MINE, NOT THE PRODUCT'S:**
Earlier PoC printed `namedNets?.length` (a Map -> undefined -> "0") and, more
importantly, never passed `namedNets` into `generateSpiceNetlist`. Passing it
(p5) makes all 86 real net names flow into the deck: `OUT`, `VCC`, `GND`,
`VDD`, `ref`, `net230`. Generic dupes are auto-disambiguated by the pipeline
(`Net_138` vs `Net_138__2_`).

**Virtual connect (user's clarification, now handled):**
Duplicate MEANINGFUL net names (GND x2 = current-sense pad + potential pad)
are NOT errors - distinct wires sharing one node. `buildNetNameMap` copies the
name per spiceId, both emit as node `GND`, and SPICE merges by name. So it is
emergent, no extra code. The tool reports it as `virtualConnects` (name +
spiceNetIds + physical annotation net UUIDs) for review, not as a warning.
